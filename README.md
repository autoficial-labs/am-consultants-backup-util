# AM Backup

A lightweight backup and restore utility for AM True Tax's Tally data, for **Windows** and **macOS**.
It watches a folder, uploads new and changed files to **Cloudflare R2**, keeps every version for
point-in-time restore, makes scheduled, highly compressed **complete backups**, and manages users and
folder-level permissions in **Cloudflare D1**. One installer covers both sides: the app can also create
and update the Cloudflare server itself, and it saves **Tally data snapshots** (ledgers and vouchers) so
backups can be viewed and compared in Tally terms.

Developed by [AFLABS](https://autoficial.ltd).

```
backup-util/
├── server/          Cloudflare Worker API (TypeScript, Hono) — D1 + R2
│   ├── migrations/  D1 schema
│   ├── scripts/     integration test, demo-data seeder, bundle.mjs (packs the Worker for the app)
│   └── wrangler.toml

│       └── worker/  The packed Worker + migrations (generated by `npm run bundle`, committed)
├── docs/            User manual (PDF) and its sources
├── PRODUCT.md       Product context used for design decisions

```

## How it works

| Piece | What it does |
|---|---|
| **Watched folder** | The admin picks a folder (usually the Tally data folder). A file watcher notices changes; a full re-scan every 30 minutes catches anything missed. |
| **Smart backups** | Each run compares the folder with a local index (size + modified time, then SHA-256). New files are added, changed files uploaded again, and files that disappear are recorded as deletions. Content is de-duplicated: identical data is never uploaded twice. Deletions are skipped if the folder can't be fully read, so a missing drive is never mistaken for "everything was deleted". |
| **Tally-aware timing** | Default (**back up between Tally entries**, for PCs where Tally never closes): while Tally (`tally.exe`, …) is open, a backup starts once Tally has saved nothing for a quiet period (3 minutes). Each company folder is copied as one checked set: the folder is snapshotted, copied, and re-checked; if Tally saved anything meanwhile, the copy is discarded and taken again at the next quiet moment. Complete backups taken while Tally is open first make a quick local copy, verify it, then compress the copy. The alternative mode **wait until Tally closes** blocks backups while Tally runs. |
| **Tally data** | When a company's files are backed up and Tally's XML server answers on this PC (port 9000), the app reads that company's ledgers (with balances) and vouchers of the last 13 months and stores a gzip JSON snapshot (at most once an hour per company, only when it changed). The **Tally data** page browses snapshots and compares two moments, or a moment with live Tally; the restore review shows what a restore changes in Tally (vouchers removed, restored, changed; balances). Tally's data files themselves are a private format and are never parsed. |
| **Storage** | File data goes to R2 at `blobs/<sha256>` (zstd-compressed). Every change is a row in D1 `versions`, which makes point-in-time restore a single query. Uploads over 48 MB use R2 multipart (32 MB parts). |
| **Complete backups** | On a schedule (daily / every N hours / weekly) the whole folder is archived as `tar` + `zstd` (level 9, 15 or 19, multithreaded, long-distance matching) with a manifest, and the oldest are pruned to "keep the latest N". No encryption, as agreed. |
| **Restore** | Pick a moment (presets 2/4/6/8 hours, a timeline you can drag, or an exact date and time) or a complete backup, choose folders and a destination, then review a visual comparison: *will be restored*, *will be replaced*, *only in destination*, *already identical*, with per-file version history. Files are verified by SHA-256 before replacing anything, and keep their original modified times. Extra files can optionally go to the Recycle Bin. |
| **Users** | One super-admin. Users are *read only* (browse and restore) or *read & write* (can also back up from their computer), with folder access *everything / only selected / all except selected / nothing*, picked from an interactive folder tree. Revoking access signs the user out everywhere immediately. |
| **Housekeeping** | A nightly cron trigger trims history older than the retention window (keeping each file's last version before the cut-off so every moment in the window stays restorable), deletes unreferenced data, and expires sessions. |

| **Server setup in the app** | *Set up a new server* (first screen) and *Server › Update server* (administrator) create or update the Worker, D1 database, R2 bucket, nightly cron, `workers.dev` address and setup key through the Cloudflare REST API, with a step-by-step token guide. Every step is idempotent and an update keeps all data. No Node.js or Wrangler is needed on the PC. The Cloudflare token is used for that call only and never stored. |

Security notes: passwords are PBKDF2-SHA256 (100k iterations); sessions are random tokens stored hashed;
logins lock for 5 minutes after 5 failures; the desktop UI never sees the session token (all server
calls go through the Rust side); restore paths are validated so archives can't write outside the
destination.

## Local testing with Localflare

Everything runs on your machine; D1 and R2 are simulated in `server/.wrangler/state`.

**Requirements:** Node 20+ (24 recommended). For the desktop app also Rust (stable, MSVC toolchain on
Windows) and the Visual Studio C++ build tools. WebView2 is already on Windows 10/11.

```powershell
cd server
npm install
npm run db:migrate:local
npx localflare
```

Localflare starts the Worker at `http://localhost:8787` and opens its dashboard
(https://studio.localflare.dev) where you can browse the D1 tables and R2 objects live. `npm run dev`
starts the same Worker without the dashboard.

Local secrets live in `server/.dev.vars` (copy `.dev.vars.example`). The `SETUP_KEY` there
(`local-setup-key` by default) is what the app asks for when creating the administrator.

**Demo data (optional):** with the server running,

```powershell
cd server
node scripts/seed-demo.mjs
```

This **wipes the local database** and creates a Tally-style folder at `demo-data/TallyData`, five days of
backed-up changes, two complete backups and three users. Sign in as `admin` / `admin12345`
(users `priya`, `rahul`, `neha` use `user12345`). Point the app's backup folder at `demo-data/TallyData`.

**Run the app against it:**

```powershell
cd app
npm install
npm run app:dev
```

On first start choose **Test server on this computer**, then create the administrator (or sign in with
the demo account).

### Tests

```powershell
cd server; npm test                          # 33 API checks: auth, permissions, uploads, snapshots, archives, Tally snapshots
cd app/src-tauri; cargo test --lib           # unit tests (paths, globbing, schedule, compression, Tally XML parsing, setup)
$env:AM_E2E_SERVER="http://localhost:8787"; cargo test --test e2e -- --nocapture
                                             # real sync → modify → delete → point-in-time restore → complete backup →
                                             # archive restore (50 MB multipart), plus a simulated Tally writing during
                                             # a backup (folder discarded, then backed up when quiet)

node tests/mock-cloudflare.mjs               # (in app/src-tauri) stand-in for the Cloudflare API
$env:AM_CF_MOCK="http://127.0.0.1:8899"; cargo test --test cloudflare -- --nocapture
                                             # server setup: retry after failure, updates, setup keys, bindings

node tests/mock-tally.mjs                    # stand-in for Tally's XML server (UTF-16, bad characters, errors)
$env:AM_TALLY_MOCK="http://127.0.0.1:9900"; cargo test --test tally -- --nocapture
```

The API test and the end-to-end test need the local server running. Both are safe to re-run; the
end-to-end test resets the local admin password with the setup key.

UI design review without the desktop shell: `npm run dev` in `app/` and open http://localhost:1420. In a
plain browser the UI talks to the local Worker directly and simulates the local-only parts (folder
scans, restores).

## Production deployment (Cloudflare)

### Recommended: from the app

On the administrator's computer, install AM Backup and choose **Set up a new server** on the first screen.
The wizard explains each step: create a free Cloudflare account, turn on R2, then open a pre-filled
Cloudflare token page (permissions: *Account Settings: Read, Workers Scripts: Edit, D1: Edit, Workers R2
Storage: Edit*), paste the token, review the checks and click **Set up server**. Then create the
administrator; the wizard shows the setup key to keep. Other computers choose **Online server** and enter the
`https://am-backup-api.<name>.workers.dev` address shown on the **Server** page.

Later app versions can carry a newer server program; **Server › Update server** uploads it and applies new
database migrations (tracked in `d1_migrations`, compatible with `wrangler d1 migrations apply`).

The Worker shipped inside the app is packed by `npm run bundle` in `server/` (the app's `app:dev` and
`app:build` scripts run it), which writes `app/src-tauri/worker/`.

### Alternative: with Wrangler

1. Sign in: `npx wrangler login`
2. Create the database and bucket:
   ```powershell
   cd server
   npx wrangler d1 create am_backup
   npx wrangler r2 bucket create am-backup-files
   ```
   Paste the printed `database_id` into `[[env.production.d1_databases]]` in `wrangler.toml`.
3. Set the setup key (a long random value; you need it once to create the administrator, and to reset
   its password if it is ever lost):
   ```powershell
   npx wrangler secret put SETUP_KEY --env production
   ```
4. Create the tables and deploy:
   ```powershell
   npm run db:migrate:remote
   npm run deploy
   ```
   Wrangler prints the Worker URL (e.g. `https://am-backup-api.<account>.workers.dev`). Optionally add a
   custom domain in `wrangler.toml` (`routes = [{ pattern = "backup.example.com", custom_domain = true }]`).
5. Open the app, choose **Online server**, enter that URL and create the administrator with the setup key.

Settings you can change in `wrangler.toml` under `[env.production.vars]`: `SESSION_DAYS` (default 30).
The nightly housekeeping cron is `17 3 * * *` (UTC).

**Limits to know:** Workers accept request bodies up to 100 MB on the Free/Pro plans; the app stays
under that automatically by using multipart uploads. R2 has no egress fees, so restores cost nothing
extra.

## Building the desktop app

```powershell
cd app
npm install
npm run app:build
```

Outputs in `app/src-tauri/target/release/bundle/` (or under your Cargo target directory if you set one):

- Windows: `nsis/AM Backup_1.0.0_x64-setup.exe` (per-user installer, no admin rights needed) and
  `msi/AM Backup_1.0.0_x64_en-US.msi`
- macOS (build on a Mac): `macos/AM Backup.app` and `dmg/AM Backup_1.0.0_*.dmg`

**Pre-configure the production server** so staff never type an address: set it at build time and the
sign-in screen offers it as "Office backup server".

```powershell
$env:AM_BACKUP_SERVER_URL="https://am-backup-api.your-account.workers.dev"; npm run app:build
```

Code signing is recommended for distribution (Windows SmartScreen and macOS Gatekeeper warn about
unsigned apps); see the Tauri signing guides.

Releases with ready-made installers are attached on the repository's GitHub *Releases* page.

On Windows the Rust toolchain must be the **x64 MSVC** one (`rustup default stable-x86_64-pc-windows-msvc`).
If another `rustc` appears earlier on `PATH`, put `%USERPROFILE%\.cargo\bin` first.

### Where things are stored on a computer

| What | Windows |
|---|---|
| Settings and session | `%APPDATA%\ltd.autoficial.ambackup\config.json` |
| Local backup index | `%APPDATA%\ltd.autoficial.ambackup\index\` |
| Logs | `%LOCALAPPDATA%\ltd.autoficial.ambackup\logs\am-backup.log` (also visible in Settings) |

The app lives in the notification area; closing the window keeps backups running (configurable).
"Start AM Backup when I sign in to Windows" is switched on automatically the first time an installed copy
runs (it can be turned off in Settings). Like Tally, it starts when a Windows user signs in.

## User manual

`docs/AM-Backup-User-Manual.pdf` is the end-user manual (A4, AFLABS branding, clickable contents and
bookmarks, written in ASD-STE100 Simplified Technical English). To rebuild it after UI changes, with the
local server (seeded with demo data) and the UI dev server running:

```powershell
node docs/manual/tools/capture.mjs   # light-theme screenshots + callout positions (headless Edge)
node docs/manual/tools/build.mjs     # figures, contents, STE check, PDF
```

Edit the text in `docs/manual/src/manual.html`. The build prints an STE check of five rules (sentence
length, a list of non-approved words, passive voice, -ing forms, contractions); it does not check the
full STE dictionary.

## Notes and decisions

- **Tally process names**: TallyPrime and Tally.ERP 9 both run as `tally.exe`; TallyPrime Server as
  `tallyprimeserver.exe`. The list is editable in Backup settings.
- **Tally open all day**: the default mode backs up between Tally entries with per-company consistency
  checks (see *Tally-aware timing*). "Back up anyway" is offered only in the *wait until Tally closes* mode.
- **Tally data** needs Tally's XML server: TallyPrime *F1 › Settings › Connectivity › Client/Server
  configuration* (acts as *Both*, port 9000); Tally.ERP 9 *F12 › Advanced Configuration*. Snapshots begin from
  the day it is turned on. The XML requests are built from Tally's documented collection export; check them
  against your Tally release (see `app/src-tauri/src/tally_data.rs`).
- **Restoring into the live folder** asks for confirmation, warns if Tally is open, and the next backup
  records the restored state, so a restore can itself be undone from history.
- **Retention** defaults: 30 days of change history, 14 complete backups, daily complete backup at
  8:00 pm with maximum compression. All adjustable by the administrator.
